# Портал ЭКРОС

Корпоративный портал для компании на ~400 сотрудников: справочник и оргструктура,
график отпусков с согласованием по цепочке, синхронизация с Active Directory,
новости, база знаний и заявки в поддержку.

Проект рассчитан на постепенное развитие: ядро (люди, роли, отпуска) стабильно,
остальные модули добавляются независимо.

## Что уже есть

### Люди и оргструктура
- **Справочник сотрудников**: поиск по фамилии, должности, телефону, почте; фильтр по подразделению;
  карточка сотрудника с контактами, руководителем, подчинёнными и запланированными отпусками.
- **Оргструктура**: дерево подразделений с руководителями и численностью, строится автоматически
  по контейнерам OU из Active Directory.
- **Профиль**: доменная учётная запись, табельный номер, цепочка руководителей, группы AD.

### Синхронизация с Active Directory (on-prem, LDAP/LDAPS)
- Пользователи, подразделения, руководители, телефоны, должности, табельные номера.
- Портал-роли выдаются по членству в группах AD (точное имя, DN или маска).
- Деактивация уволенных (пропавших из выдачи) без потери истории.
- Протокол запусков, dry-run (проверка без записи), инкрементальный режим по `whenChanged`,
  защита от «пустой выдачи», запуск из интерфейса и по cron.
- **Вход по доменному паролю** (LDAP bind): пароль в портале не хранится. При первом входе
  карточка сотрудника автоматически создаётся из каталога.

### График отпусков
- Выбор года графика прямо в форме заявления (если открыто несколько периодов).
- Заявления с проверкой остатка дней, пересечений и сроков; расчёт календарных дней
  без нерабочих праздничных дней (ст. 120 ТК РФ) по производственному календарю.
- **Согласование по цепочке**: маршруты настраиваются в интерфейсе (руководитель → кадры → директор
  и любые комбинации). Маршрут выбирается по подразделению → роли → по умолчанию.
- Маршрут «замораживается» в заявлении при отправке: изменение настроек не переписывает
  уже идущие согласования.
- Очередь согласования, комментарии, история решений, отзыв заявления, уведомления участникам.
- **Сводный график**: сотрудники × месяцы с цветными полосами отпусков, фильтр по подразделению,
  выгрузка CSV (для Excel) и печать.
- Календарь отпусков по дням, «кто в отпуске сегодня», отпуска команды для руководителя.
- Периоды графика (сбор заявлений → согласование → утверждение → закрытие), права на дни,
  переносы с прошлого года, производственный календарь.

### Прочее
- **Новости и объявления** (закрепление, рубрики, простой markdown).
- **База знаний** (разделы, теги, поиск, markdown).
- **Заявки в поддержку** (ИТ/доступы/кадры/АХО): статусы, исполнитель, переписка,
  внутренние комментарии для исполнителей, уведомления заявителю.
- **Глобальный поиск** по сотрудникам, новостям, базе знаний, заявкам и заявлениям.
- **Уведомления** в портале (+ опционально письма).
- **Журнал аудита** значимых действий и полная админка Django.

## Быстрый старт

Требуется Python 3.12+.

```bash
# 1. окружение
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt

# 2. локальные настройки
cp .env.example .env
# для демо достаточно оставить AD_SERVER пустым — включится демо-каталог

# 3. база и данные
python manage.py migrate
python manage.py seed_demo        # 400 сотрудников, графики, новости, заявки

# 4. запуск
python manage.py runserver 0.0.0.0:8000
```

Если `python -m venv`/`pip` в системе недоступны (закрытый контур), зависимости можно
положить рядом с проектом и запускать через обёртку:

```bash
mkdir -p .bootstrap
python3 -c "import urllib.request;open('.bootstrap/get-pip.py','wb').write(urllib.request.urlopen('https://bootstrap.pypa.io/get-pip.py').read())"
python3 .bootstrap/get-pip.py --target .bootstrap/vendor
PYTHONPATH=.bootstrap/vendor python3 -m pip install --target .bootstrap/vendor Django ldap3

./scripts/manage.sh migrate
./scripts/manage.sh seed_demo
./scripts/manage.sh runserver 0.0.0.0:8000
```

`scripts/manage.sh` сам подхватывает `.venv` или `.bootstrap/vendor`.

Портал: <http://127.0.0.1:8000/>

### Учётные записи после `seed_demo`

| Кто | Логин | Пароль |
|-----|-------|--------|
| Администратор портала (локальная УЗ) | `portal.admin` | `PortalAdmin#2026` |
| Любой сотрудник из демо-каталога | логин из справочника (например `a.ivanov`) | любой пароль от 3 символов; пароль `wrong` имитирует отказ |
| Админка Django | `portal.admin` | тот же |

> Смените пароль администратора перед публикацией портала: `python manage.py changepassword portal.admin`.

Роли демо-сотрудников раздаются по группам AD автоматически: руководители, кадры, директора,
администраторы портала.

## Демонстрационные данные

`python manage.py seed_demo` создаёт:

- роли портала и их маппинг на группы AD (`ECROS-Portal-Users`, `-Managers`, `-HR`, `-Directors`, `-Admins`);
- 4 вида отпусков, праздничные дни на 3 года, периоды графиков на текущий и следующий год;
- 3 маршрута согласования (стандартный, для отдела кадров, для директоров);
- 400 сотрудников, ~27 подразделений, руководителей всех уровней (из демо-каталога);
- 5 новостей, 6 статей базы знаний, 6 быстрых ссылок, 12 заявок в поддержку;
- ~75 заявлений на отпуск в разных статусах, проведённых через настоящий движок согласования.

Полезные флаги: `--no-sync`, `--no-vacations`, `--admin-username`, `--admin-password`, `--seed`.

Чтобы начать с чистого листа: `rm var/db.sqlite3 && python manage.py migrate && python manage.py seed_demo`.

## Интеграция с Active Directory

### Что нужно в домене

1. **Служебная учётная запись** для чтения каталога (например `svc-portal`), достаточные права:
   чтение свойств пользователей и групп в OU сотрудников. Пароль не должен истекать.
2. **OU-структура**: подразделения портала строятся по контейнерам OU в `distinguishedName`.
   Контейнеры-«склады» вроде `OU=Сотрудники` и `OU=Users` игнорируются (настраивается в
   `apps/accounts/utils.py`, `IGNORED_OU_NAMES`).
3. **Группы портала** (необязательно, но удобно): `ECROS-Portal-HR`, `ECROS-Portal-Managers`,
   `ECROS-Portal-Directors`, `ECROS-Portal-Admins`. Их имена сопоставляются ролям в разделе
   «Роли и доступ».
4. **Атрибуты**: `sAMAccountName`, `mail`, `givenName`, `sn`, `middleName`, `displayName`, `title`,
   `department`, `telephoneNumber`/`ipPhone`, `mobile`, `physicalDeliveryOfficeName`, `l`,
   `employeeID`, `manager`, `memberOf`, `userAccountControl`, `objectGUID`, `whenChanged`.
   Заполненный `manager` важен: он определяет первого согласующего в графике отпусков.

### Настройка портала

Заполните в `.env`:

```ini
AD_ENABLED=True
AD_PROVIDER=ldap
AD_SERVER=dc01.ecros.local
AD_PORT=636                 # 389 для LDAP, 636 для LDAPS
AD_USE_SSL=True             # для LDAPS
AD_BASE_DN=DC=ecros,DC=local
AD_USER_SEARCH_BASE=OU=Сотрудники,DC=ecros,DC=local
AD_BIND_DN=CN=svc-portal,OU=Service Accounts,DC=ecros,DC=local
AD_BIND_PASSWORD=...
AD_DOMAIN_NETBIOS=ECROS
```

Проверка подключения и пробный прогон:

```bash
python manage.py ad_check          # связь, базовая выдача, пример записи
python manage.py ad_sync --dry-run # что изменится, без записи в БД
python manage.py ad_sync           # полная синхронизация
python manage.py ad_sync --incremental
```

В интерфейсе: **Кадры → Синхронизация AD** — состояние связи, история запусков, кнопки
«Проверить (dry-run)» и «Синхронизировать сейчас».

### Как работает сопоставление

| Данные AD | Куда попадает в портале |
|-----------|-------------------------|
| `objectGUID` (резерв — `sAMAccountName`) | ключ сопоставления сотрудника |
| контейнеры OU из `distinguishedName` | дерево подразделений (`Department`) |
| `department` | название конечного подразделения |
| `manager` | непосредственный руководитель и первый согласующий |
| `memberOf` | роли портала через маски групп в разделе «Роли и доступ» |
| `userAccountControl` (бит ACCOUNTDISABLE) | запрет входа и признак «отключён» |
| пропавшие из выдачи | деактивация (`is_active=False`), история сохраняется |

Руководитель подразделения определяется по фактической подчинённости: приоритет у сотрудника
подразделения с наибольшим числом подчинённых внутри него, затем у того, кто ведёт дочерние отделы.

### Вход сотрудников

Портал делает LDAP simple bind от имени сотрудника (`ECROS\login` или `login@domain`).
Успешный bind — вход разрешён. Доменный пароль в портале **не хранится**.
Первый вход создаёт карточку в портале, если её ещё нет.

Резервный канал — локальные учётные записи (`source=local`, суперпользователи). Он нужен,
если контроллер домена недоступен; отключается через `PORTAL_ALLOW_LOCAL_PASSWORD=False`.

## График отпусков и маршруты согласования

### Маршрут: понятия

- **Маршрут** (`ApprovalChainTemplate`) — именованная цепочка шагов и условия применения:
  подразделение, роли заявителя, виды отпуска, приоритет, «по умолчанию».
- **Шаг** (`ApprovalChainStep`) — тип согласующего:
  - непосредственный руководитель;
  - руководитель руководителя;
  - руководитель подразделения;
  - директор направления;
  - отдел кадров;
  - сотрудник с ролью;
  - конкретный сотрудник.
- **Пропускать шаг** — если согласующий не найден (нет руководителя, роль без участников),
  шаг пропускается. Снимите флаг, чтобы заявление останавливалось с ошибкой и требовало настройки.

### Выбор маршрута

1. Маршрут, привязанный к подразделению заявителя (включая вложенные) — самый приоритетный.
2. Маршрут, привязанный к ролям заявителя.
3. Маршрут «по умолчанию».

Внутри одной категории решает `priority` (меньше — важнее).

### Движение заявления

```
Черновик → На согласовании (шаг 1 → шаг 2 → …) → Согласовано
                                   ↘ Отклонено (с причиной)
Согласовано / На согласовании → Отозвано (автором; утверждённое — кадры)
```

- При отправке маршрут **фиксируется**: шаги копируются в заявление, поэтому изменения
  шаблона не «переписывают» идущие согласования.
- Каждый шаг видит только текущий согласующий; остальные участники — после своей очереди.
- Отклонение требует причины; комментарий виден автору.
- Все решения и отправки пишутся в журнал аудита, участники получают уведомления.

### Проверки при отправке

- дата окончания не раньше начала, дата начала — в году периода;
- приём заявлений в периоде открыт;
- дни считаются без праздничных (производственный календарь заполняется в
  *Настройки отпусков → Производственный календарь*);
- остаток дней покрывает запрос (учитываются и заявления на согласовании);
- нет пересечения с другими своими заявлениями;
- до начала не меньше `VACATION_MIN_NOTICE_DAYS` дней (кадры и администраторы могут оформлять
  в обход — срочные случаи).

### Настройка «с нуля»

1. **Виды отпусков** — *Настройки отпусков → Виды отпусков* (по умолчанию: ежегодный 28 дней,
   дополнительный, без сохранения з/п, учебный).
2. **Период** — *Периоды*: год, статус, срок приёма. При создании периода права на дни
   оформляются всем активным сотрудникам.
3. **Маршруты** — *Маршруты согласования*: создайте хотя бы один маршрут «по умолчанию»
   (например, руководитель → кадры), иначе заявления не смогут уйти на согласование.
4. **Ответственные по ролям** — *Роли и доступ*: укажите, кому адресуются шаги «Отдел кадров»
   и «Директор направления».
5. **Права на дни** — *Права на отпуск*: положения, перенос с прошлого года, примечания.

## Роли и права

| Возможность | Сотрудник | Руководитель | Кадры | Администратор |
|-------------|-----------|--------------|-------|---------------|
| Справочник, оргструктура, новости, база знаний | ✓ | ✓ | ✓ | ✓ |
| Создать заявление на отпуск | ✓ | ✓ | ✓ (+ за других) | ✓ |
| Согласовать заявление (свой шаг) | — | ✓ | ✓ (обход при необходимости) | ✓ |
| Сводный график, календарь | ✓ | ✓ | ✓ | ✓ |
| Периоды, права на дни, виды отпусков, календарь | — | — | ✓ | ✓ |
| Маршруты согласования | — | — | ✓ | ✓ |
| Синхронизация AD, роли, админка | — | — | — | ✓ |
| Заявки в поддержку: обработка всех | — | — | ✓ | ✓ |
| Новости и база знаний: публикация | — | — | ✓ | ✓ |

Роли назначаются автоматически по группам AD при синхронизации и входе; вручную можно
донастроить в «Роли и доступ» (ответственный по роли) и в админке Django (участники).

## Архитектура и структура кода

```
EcrosPortal/
├── config/                 настройки Django, корневые URL, загрузчик .env
├── apps/
│   ├── accounts/           сотрудники, подразделения, роли, аудит, AD-интеграция
│   │   ├── ad/             слой каталога: base, ldap_provider, mock_provider, sync, factory
│   │   ├── management/     ad_sync, ad_check, seed_demo
│   │   ├── auth.py         бэкенды аутентификации (AD bind + локальный резерв)
│   │   ├── permissions.py  проверки ролей для вьюх
│   │   └── middleware.py   обязательная авторизация
│   ├── vacations/          график отпусков
│   │   ├── models.py       периоды, права, маршруты, заявки, шаги, праздники
│   │   ├── services.py     расчёт дней, выбор/разбор маршрута, согласование, уведомления
│   │   ├── views.py        интерфейс: мои отпуска, согласование, график, настройки
│   │   └── management/     vacation_reminders
│   └── portal/             главная, справочник, новости, база знаний, заявки, поиск, уведомления
├── templates/              Django-шаблоны (base.html + разделы)
├── static/                 дизайн-система CSS и небольшой JS, без внешних библиотек
├── scripts/smoke.py        дымовая проверка страниц под разными ролями
├── deploy/                 systemd, nginx, cron
├── Dockerfile, docker-compose.yml
└── manage.py
```

Ключевые проектные решения:

- **Провайдер каталога за интерфейсом** (`AdDirectory`): боевой LDAP, демо-генератор или
  собственный источник (например, выгрузка из 1С ЗУП) подключаются без изменения синхронизации.
- **Бизнес-логика отпусков в `services.py`**, а не во вьюхах: правила проверяемы тестами,
  их можно переиспользовать из команд, API и будущего мобильного клиента.
- **Маршрут — снимок**: шаги копируются в заявление, поэтому история согласований неизменяема.
- **Источник истины по людям — AD**, портал хранит только то, что нужно для процессов
  (роли, отпуска, заявки, контент).

## Развёртывание

### Вариант 1: Linux + systemd + nginx (рекомендуется)

```bash
sudo useradd -r -s /usr/sbin/nologin -d /opt/ecros-portal ecros
sudo mkdir -p /opt/ecros-portal && sudo chown ecros: /opt/ecros-portal

# код
sudo -u ecros git clone <repo> /opt/ecros-portal
cd /opt/ecros-portal
sudo -u ecros python3 -m venv .venv
sudo -u ecros .venv/bin/pip install -r requirements.txt

# настройки
sudo -u ecros cp .env.example .env
sudo -u ecros nano .env        # DJANGO_DEBUG=False, SECRET_KEY, AD_*, БД, ALLOWED_HOSTS

# база и статика
sudo -u ecros .venv/bin/python manage.py migrate
sudo -u ecros .venv/bin/python manage.py collectstatic --noinput
sudo -u ecros .venv/bin/python manage.py createsuperuser   # или seed_demo для пилота
```

Файлы запуска — в каталоге `deploy/`:

```bash
sudo cp deploy/ecros-portal.service /etc/systemd/system/
sudo cp deploy/nginx.conf.example /etc/nginx/sites-available/ecros-portal
sudo ln -s /etc/nginx/sites-available/ecros-portal /etc/nginx/sites-enabled/
sudo systemctl daemon-reload && sudo systemctl enable --now ecros-portal
sudo nginx -t && sudo systemctl reload nginx
```

### Вариант 2: Docker

```bash
cp .env.example .env      # укажите DJANGO_SECRET_KEY, AD_*, пароль БД
docker compose up -d --build
docker compose exec web python manage.py seed_demo     # для тестового контура
```

### PostgreSQL

Для боевой эксплуатации включите PostgreSQL (проще бэкапы и параллельная нагрузка):

```ini
DJANGO_DB_ENGINE=postgres
DJANGO_DB_NAME=ecros_portal
DJANGO_DB_USER=ecros
DJANGO_DB_PASSWORD=...
DJANGO_DB_HOST=127.0.0.1
```

Затем `python manage.py migrate`. Код одинаково работает на SQLite и PostgreSQL.

## Регламентные задания

`deploy/crontab.example`:

```cron
# синхронизация с AD — каждый час
15 * * * * root cd /opt/ecros-portal && sudo -u ecros .venv/bin/python manage.py ad_sync --incremental --quiet >> var/cron.log 2>&1

# напоминания по отпускам — ежедневно в 09:00
0 9 * * * root cd /opt/ecros-portal && sudo -u ecros .venv/bin/python manage.py vacation_reminders >> var/cron.log 2>&1
```

## Безопасность

- Пароли домена в портале не хранятся: проверка выполняется bind-запросом к AD.
- Защита от перебора: ограничение попыток входа по IP+логину (`PORTAL_LOGIN_MAX_ATTEMPTS`).
- CSRF-защита на всех формах, cookie `HttpOnly`, `SameSite=Lax`, обязательная авторизация на всех
  страницах (middleware + декораторы), запрет встраивания в iframe.
- Проверки прав на уровне объектов: нельзя открыть чужое заявление, заявку или раздел настроек.
- Журнал аудита: отправка и решения по отпускам, изменения настроек, синхронизация AD.
- Рекомендуется: HTTPS (nginx), `DJANGO_DEBUG=False`, `DJANGO_SECRET_KEY` из секрета,
  LDAPS или StartTLS в закрытом контуре, резервные копии БД.
- Периодически проверяйте `python manage.py check --deploy`.

## Брендинг

Оформление портала построено на фирменной палитре ГК «ЭКРОС» (взята с корпоративного
сайта <https://www.ecohim.ru/>). Все цвета заданы переменными в начале
`static/css/app.css`, поэтому смена палитры — это правка одного блока `:root`.

| Роль в интерфейсе | Цвет | Где используется |
|-------------------|------|------------------|
| Основной зелёный | `#00875c` | кнопки-действия, ссылки, активный пункт меню, акценты |
| Тёмный зелёный (hover, pressed) | `#006b49` | наведение на кнопки, заголовки блоков |
| Глубокий зелёный | `#004b33` | акцентный фон, боковая панель `#003d29` |
| Светлый тинт | `#e7f4ee` | плашки, бейджи, подсветка строк |
| Акцент яркий | `#00a651` | градиенты логотипа и акцентных карточек |
| Янтарный (предупреждения) | `#a06300` | статусы «на согласовании», приоритеты |
| Красный (ошибки, отказ) | `#cf3f34` | отклонение, удаление, ошибки формы |
| Нейтральные | `#f3f5f6`, `#f8f8f8`, `#e6e6e6`, `#d9d9d9` | фон, таблицы, границы |
| Текст | `#222222`, `#5f5f5f`, `#687076` | заголовки, основной и приглушённый текст |

Дополнительно:

- **Типографика** — Rubik (как на сайте компании), файлы лежат локально в
  `static/fonts/` с подмножествами кириллица/латиница, лицензия OFL-1.1
  (см. `static/fonts/LICENSE.md`). Внешние CDN не используются — портал работает
  в изолированной сети.
- **Контраст** — все основные пары «текст на фоне» проверены на WCAG AA
  (минимум 4.55:1), приглушённый текст сознательно темнее, чем на маркетинговом
  сайте, ради читаемости на рабочих мониторах.
- **Цвета видов отпуска и рубрик новостей** хранятся в базе и задаются в интерфейсе
  («Виды отпусков», Django-админка). Для существующих установок значения по умолчанию
  приведены к фирменной гамме миграциями `vacations/0002_brand_colors` и
  `portal/0002_brand_colors`.

## Что дальше

Каркас готов к расширению. Ближайшие очевидные шаги:

- **Приказы по отпускам** (печатные формы Т-6/Т-7, выгрузка в 1С ЗУП).
- **SSO без пароля** (Kerberos/IWA или OIDC через Entra ID) поверх текущего бэкенда.
- **Согласование других заявок** — командировки, материальная помощь: механика маршрутов уже общая.
- **Кадровые события** (приём/перевод/увольнение) с задачами для руководителя и кадров.
- **Онбординг/оффбординг** с чек-листами и напоминаниями.
- **Учёт рабочего времени и отсутствий** (больничные, удалёнка) поверх календаря.
- **Интеграция с мессенджером** (Mattermost/Telegram) для уведомлений.
- **Аналитика**: загруженность подразделений, остатки отпусков, просроченные согласования.
- **REST API** (`/api/`) для мобильного клиента — `services.py` к этому готов.
